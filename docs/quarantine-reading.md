# Bounded quarantine reads and checksum-bound scan receipts — #117

## Delivered

`EvidenceObjectStorage.readQuarantined(reference, maxBytes)` reads a complete nonempty quarantined object with a caller limit of 1..10 MiB. The local/test filesystem adapter implements it; the production gate always rejects it. File and URL key layouts already generated by Cadence remain supported.

`QuarantinedEvidenceScanner` is an internal worker building block, not a new endpoint or scheduled worker. It validates the expected SHA-256 and limit, reads bounded bytes, independently rejects a broken adapter's empty/oversized result, owns a copy, verifies SHA-256 and scans those exact bytes. The returned `QuarantineScanReceipt` contains checksum, observation time and explicit verdict. Null/exception scanner results and unexpected mutation of input become ERROR. Storage failures never reach the scanner.

The receipt is an in-memory observation, not persisted scan provenance. Scanner engine/signature versions are unavailable from the current port and are not invented. A receipt does not approve evidence, promote it to READY, bind a Job attempt or authorize a database update.

## Architecture / runtime flow

Future authorized worker context → internal reference + expected checksum + byte limit → bounded storage read → independent bounds and SHA-256 verification → scanner → checksum/time/verdict receipt → future fenced completion transaction.

The Spring service uses `Propagation.NEVER`: an existing transaction is rejected before I/O. A proxy-based integration test verifies this and verifies that successful I/O opens no transaction. Direct `new` construction bypasses Spring interception, so runtime workers must inject the bean and call it outside claim/completion transactions. Upload registration was subsequently migrated by the [upload transaction slice](file-upload-transactions.md).

Storage does not enforce tenant membership. Internal references and expected checksums must be selected from authorized, scoped evidence records. No HTTP client can invoke this new method. Future worker selection must recheck active Workspace/Brand state and fence writes by lease and attempt.

## Security Review / threat model

Assets: quarantine files, private host paths, storage/memory capacity and integrity of scan observations. Callers: internal workers; HTTP upload callers remain subject to OWNER and Workspace checks. Boundaries: persisted references, filesystem content and adapter outcomes.

| Threat | Protection | Verification |
| --- | --- | --- |
| Traversal, URL/absolute path, Windows alternate streams/devices | Literal quarantine prefix, bounded ASCII path segments, no dot segments/backslashes/colons/encoded paths/reserved device names; containment check | Parameterized invalid-reference fixtures, read/write rejection before file creation |
| Symlink redirects / non-file objects | Check canonical root, every parent and target; reject links/other file types; open final file with NOFOLLOW_LINKS | Linux root/parent/file symlink fixtures; target remains unchanged after rejected writes |
| Oversized object or growth during read | Channel-size precheck plus reading at most limit+1; independent application cap; bounded writes | Exact boundary and oversized-object tests, invalid limits, oversized mock adapter result |
| Tampered stored bytes | SHA-256 equality before scanner; owned copy and post-scan mutation check | Real storage tampering, mocked checksum mismatch and scanner mutation tests |
| Scanner/storage outage or private error leakage | Fixed storage failure codes, no raw provider causes; null/exception scan maps to ERROR | Failure and redaction tests, no scanner call on read failure |
| Holding DB connections during I/O | NEVER transaction propagation on injected service | Real Spring proxy tests for rejection and transaction-free execution |

No new credentials, dependencies, SQL, shell commands or public download API are introduced. Existing HTTP authorization suites remain active. Raw content, paths and provider exceptions are not logged by the new component.

## Filesystem security assumptions and limitations

This remains a local/test adapter. The configured root must be a canonical local-disk directory with its ancestors and contents writable only by the application/developer identity. Do not use shared writable roots, network shares or mounts with untrusted writers. Existing symlink/junction paths are rejected; path checks and NOFOLLOW_LINKS are not a cross-platform guarantee against a hostile local process concurrently replacing ancestor directories. Hard links, filesystem administration and host compromise are outside this adapter's isolation boundary. These restrictions must be enforced through host permissions, not inferred from filename validation.

Java documents race-resistant relative directory operations in [SecureDirectoryStream](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/SecureDirectoryStream.html), whose availability depends on the filesystem provider. The portable local adapter does not claim that guarantee. See also [Files](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/Files.html) for path and channel semantics. Production continues to deny storage access until a separately verified adapter is supplied.

Read size is bounded, but local filesystem I/O has no portable total deadline here. Production adapters need explicit deadlines and quotas. The current filesystem write uses atomic replacement as before; checksum verification detects content substitution, but immutable provider object versions and orphan retention still need design.
