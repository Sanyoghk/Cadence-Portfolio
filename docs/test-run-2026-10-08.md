## Как это работает и архитектурное решение

Использованы существующие tests и scripts, без ослабления assertions или отключения security.
Maven проверяет compilation, unit/domain/HTTP/persistence/concurrency, Spotless и JaCoCo.
Testcontainers запускает disposable PostgreSQL/MinIO/ClamAV/renderer. Python report gates
отвергают missing/skipped/failed обязательные integration reports. Linux launcher отдельно
проверяет filesystem scenarios, недоступные на Windows.

Окружение: Windows, Temurin Java 21.0.11, Docker Engine 29.8.1, Linux containers.
PostgreSQL test logs показывают version 17.11. Docker Desktop первоначально был остановлен;
он запущен установленным executable. Sandbox не разрешает Docker named pipe, поэтому
Maven/Docker/startup commands выполнены с approved escalation. Security settings tests сохранены.

## Runtime Flow

```text
Maven clean verify → compilation → JUnit / Spring contexts
    → Testcontainers disposable providers → Surefire XML
    → JAR packaging / Spotless / JaCoCo
    → Python mandatory-report gates

Docker Linux JVM → filesystem tests (including symlinks)
Docker pinned renderer → Python tests
Packaged local JAR → health 200 / anonymous protected request 401 → process stopped
```

## Edge Cases и warnings

Windows skips только: `rejectsLinkedFileForReadAndWrite`, `rejectsLinkedStorageRoot`,
`rejectsLinkedParentForReadAndWrite`. Все три вошли в Linux35/35 без skips.

Первый Python run в sandbox default temp завершился PermissionError, а не product assertion
failure. После выбора workspace temp final suite10/10 прошёл. Docker preflight первоначально
обнаружил stopped daemon, затем sandbox named-pipe denial; approved full run получил working engine.

В Maven log есть JVM CDS/bootstrap-classpath warning и Hikari closed-connection validation
warnings вокруг lifecycle disposable PostgreSQL test databases. Assertions и report gates
прошли; warnings не подавлялись. Они не доказывают проблему production pool configuration.

## Непроверенные аспекты и Production considerations

Этот run local, не новый GitHub Actions run; push/merge/deployment не выполнялись.
Enforcing AppArmor profile на отдельном Ubuntu host в этой задаче не проверялся:
Docker Desktop renderer tests не заменяют этот CI/deployment gate. Real provider accounts,
live Clerk/OAuth/AI, production cloud IAM/TLS/sandbox, load/backup/PITR и frontend E2E
не проверены. Новая dependency vulnerability scan/SAST здесь не запускалась; это отдельные
проверки, а не отсутствующие JUnit tests. Не считать старый OSV result свежим scan.

## Что мне важно понять и что изучить

1. Testcontainers: реальные disposable services дают проверку PostgreSQL/provider поведения,
   которую H2 и mocks не заменяют.
2. Report gate: machine-readable контроль состава suite; отсутствие failure само по себе
   недостаточно, если нужный integration test вообще skipped.
3. Platform-specific testing: Windows не выполняет Linux symlink scenarios; отдельный
   Linux35/35 закрывает именно эту границу, не production AppArmor qualification.

Факты: все результаты таблицы получены новым запуском на aa6da33; application code неизменен.
Инженерный вывод: текущий source проходит существующий local verification contract с Docker.
Assumptions/ограничения: tests покрывают свои scenarios; production, live providers и новый
remote CI требуют отдельного доказательства. Whole #121 acceptance criteria всё ещё не закрыты.
